## نصب تک‌دستوری / One-command install

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/eris4444/eris-tunnel/main/install.sh)
```

بعد از نصب، آدرس پنل به همراه نام کاربری و رمز عبور نمایش داده می‌شود.
_After installation the panel URL, username and password are printed._

گزینه‌های اختیاری / optional flags:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/eris4444/eris-tunnel/main/install.sh) --port 8686 --username admin --lang en
```

| فلگ | توضیح |
| --- | --- |
| `--port <n>` | پورت پنل (پیش‌فرض: هنگام آپدیت پورت فعلی حفظ می‌شود، در نصب تازه یک پورت تصادفی) |
| `--username <name>` | نام کاربری ادمین (پیش‌فرض: `admin`) |
| `--password <pass>` | رمز عبور (پیش‌فرض: تصادفی و امن) |
| `--lang fa\|en` | زبان پیش‌فرض پنل |
| `--branch <name>` | برنچ سورس (پیش‌فرض: `main`) |

## امکانات / Features

- 🔐 **تانل SSH** — فوروارد `Local (-L)`، `Remote (-R)` و `SOCKS (-D)` با چند قانون روی یک تانل
- 🔁 **بک‌هاول** — پشتیبانی کامل از `tcp`, `tcpmux`, `udp`, `ws`, `wsmux`, `wss`, `wssmux` در دو نقش سرور و کلاینت
- ♻️ **اتصال مجدد خودکار** — هر تانل یک سرویس systemd با `Restart=always` است
- 📊 **داشبورد زنده** — CPU، رم، دیسک، پهنای باند لحظه‌ای، اتصالات فعال و آپ‌تایم
- ⚿ **مدیریت کلید SSH** — ساخت کلید `ed25519` یا وارد کردن کلید موجود، مستقیم از پنل
- 📜 **لاگ زنده** — خروجی `journalctl` هر تانل داخل پنل
- 🌐 **دوزبانه** — فارسی (RTL) و انگلیسی
- 🪶 **سبک** — فقط `fastapi` و `uvicorn`؛ بدون دیتابیس خارجی، بدون Node.js، بدون مرحله build

## دستورات مدیریتی / CLI

پس از نصب دستور `eris` در دسترس است:

```bash
eris info          # آدرس پنل و تنظیمات فعلی
eris status        # وضعیت سرویس پنل
eris log 200       # آخرین ۲۰۰ خط لاگ پنل
eris restart       # ری‌استارت پنل
eris reset         # ساخت رمز جدید برای ادمین
eris port 9000     # تغییر پورت پنل
eris update        # نصب مجدد آخرین نسخه (تنظیمات حفظ می‌شود)
eris uninstall     # حذف کامل
```

## راهنمای کامل تانل SSH

### مرحله ۱ — ساخت یا وارد کردن کلید (اختیاری، فقط اگر با کلید وصل می‌شوید)

از تب **کلیدهای SSH** روی «ساخت کلید جدید» بزنید (یک کلید `ed25519` می‌سازد) یا کلید
موجودتان را با «وارد کردن کلید» اضافه کنید. کلید عمومی که نمایش داده می‌شود را کپی کنید
و روی **سرور مقصد** (نه سروری که پنل رویش نصب است، بلکه سروری که می‌خواهید بهش وصل شوید)
با دست به فایل زیر اضافه کنید:

```bash
echo "ssh-ed25519 AAAA... eris-tunnel:my-key" >> ~/.ssh/authorized_keys
```

پنل این مرحله را خودکار انجام نمی‌دهد چون به سرور مقصد دسترسی SSH از قبل ندارد — این
تنها قدمی است که باید دستی انجام شود.

### مرحله ۲ — ساخت تانل

تب **تانل SSH** ← «تانل جدید»:

| فیلد | توضیح |
| --- | --- |
| نام | یک اسم دلخواه بدون فاصله، مثلاً `tokyo-relay` |
| آدرس سرور | IP یا دامنه‌ی سروری که می‌خواهید بهش SSH بزنید |
| پورت SSH | معمولاً `22` |
| کاربر | معمولاً `root` |
| نوع احراز هویت | «کلید SSH» (امن‌تر و پیشنهادی) یا «رمز عبور» |

اگر «رمز عبور» را انتخاب کنید، بسته‌ی `sshpass` باید روی سرور پنل نصب باشد (نصب‌کننده
خودش این را نصب می‌کند؛ اگر داشبورد پنل هشدار زرد «sshpass نصب نیست» را نشان می‌دهد یعنی
این بسته موجود نیست و باید با کلید وصل شوید).

### مرحله ۳ — قوانین فوروارد

| نوع | کاربرد | مثال |
| --- | --- | --- |
| `Local (-L)` | پورتی روی **سرور مقصد** را روی **همین سرور پنل** در دسترس می‌کند | بایند `0.0.0.0:8080` → مقصد `127.0.0.1:80` |
| `Remote (-R)` | پورتی روی **همین سرور پنل** را روی **سرور مقصد** منتشر می‌کند | بایند `0.0.0.0:443` ← مقصد `127.0.0.1:443` |
| `SOCKS (-D)` | یک پراکسی SOCKS5 روی همین سرور پنل می‌سازد که ترافیک از طریق سرور مقصد خارج می‌شود | بایند `127.0.0.1:1080` |

> برای فوروارد `Remote` باید روی **سرور مقصد** در فایل `/etc/ssh/sshd_config` مقدار
> `GatewayPorts yes` تنظیم و سرویس ssh ری‌استارت شده باشد، وگرنه پورت فقط روی
> `127.0.0.1` همان سرور مقصد باز می‌شود و از بیرون در دسترس نیست.

می‌توانید چند قانون را با «افزودن قانون» به یک تانل اضافه کنید — نیازی به ساخت چند تانل
جدا برای چند پورت نیست.

### مرحله ۴ — تست و ذخیره

قبل از ذخیره، دکمه‌ی **تست اتصال** را بزنید. اگر پیغام «اتصال موفق بود» را دیدید یعنی
احراز هویت درست است. اگر خطا داد، متن خطا (که خروجی خام ssh است) معمولاً دقیقاً می‌گوید
مشکل کجاست: `Permission denied` یعنی کلید/رمز اشتباه است، `Connection timed out` یعنی
فایروال سرور مقصد پورت ۲۲ را بسته یا IP اشتباه است.

با «ذخیره» تانل به‌صورت یک سرویس systemd ساخته و (اگر «شروع خودکار» تیک خورده باشد)
بلافاصله استارت می‌شود.

## راهنمای کامل بک‌هاول

Backhaul فقط یک **تونل خام TCP/UDP** بین دو سرور است — خودش هیچ رمزنگاری VPN یا کانفیگ
کلاینتی (vless/vmess) تولید نمی‌کند. برای ساخت یک مسیر کامل باید یک نرم‌افزار پروکسی
(مثل Xray از طریق Marzban یا 3x-ui) روی یکی از دو سرور اجرا شود و Backhaul فقط ترافیک
کاربر را بین دو سرور جابه‌جا کند.

### مفهوم پایه: نقش «سرور» در برابر «کلاینت»

این مهم‌ترین نکته‌ای است که باید قبل از هر چیز درک شود:

- **نقش «سرور»** روی سروری تنظیم می‌شود که **آدرسش عمومی/در دسترس کاربر نهایی** باشد.
  این سرور هم پورت کنترل تونل (مثلاً `3080`) را باز می‌کند و هم هر پورتی که در لیست
  «پورت‌ها» گذاشته باشید (مثلاً `443`) را مستقیماً برای اتصال کاربران باز می‌کند.
- **نقش «کلاینت»** روی سروری تنظیم می‌شود که **سرویس واقعی** (مثلاً Xray) رویش در حال
  اجراست. این سرور به سمت «سرور» وصل می‌شود و وقتی یک اتصال کاربر از طریق تونل می‌رسد،
  آن را به `127.0.0.1:همان‌پورت` روی **خودش** تحویل می‌دهد.

به زبان ساده: **جهت اتصال کاربر همیشه به سمت «سرور» است، و «کلاینت» جایی است که سرویس
واقعی محلی اجرا می‌شود.**

### پیش‌نیاز: نصب باینری (روی هر دو سرور)

تب **بک‌هاول** ← اگر بالای صفحه نوشته «هنوز نصب نشده»، دکمه‌ی **نصب Backhaul** را بزنید.
آخرین نسخه از مخزن رسمی [Musixal/Backhaul](https://github.com/Musixal/Backhaul) متناسب
با معماری سرور (amd64/arm64) دانلود می‌شود.

### سناریوی کامل و واقعی: کاربر به IP ایران وصل شود، ولی سایت‌ها IP خارج ببینند

این رایج‌ترین سناریوی استفاده از این پنل است، پس با جزئیات کامل توضیح داده می‌شود.
فرض:

- سرور خارج: `185.31.200.156` — اینجا Xray واقعی (از طریق Marzban یا 3x-ui) اجرا می‌شود
  و باید این IP در اینترنت دیده شود.
- سرور ایران: کاربران باید به IP همین سرور وصل شوند.
- پورت اینباند انتخابی: `8443` (هر پورت بازی مثل `2053`، `2083`، `2087` هم قابل استفاده
  است — فقط باید هم روی خود اینباند Marzban و هم در تنظیمات بک‌هاول یکی باشد).

از آنجا که کاربر باید به **ایران** وصل شود، طبق قانون بالا:

- **سرور ایران = نقش «سرور»** (چون IP‌اش عمومی/در دسترس کاربر است)
- **سرور خارج = نقش «کلاینت»** (چون سرویس واقعی Xray آنجاست)

#### قبل از شروع: مطمئن شوید پورت آزاد است

روی **هر دو سرور** بزنید:

```bash
ss -tlnp | grep :8443
```

اگر خروجی خالی بود پورت آزاد است. اگر توسط چیز دیگری اشغال شده، یا آن سرویس را جابه‌جا
کنید یا از پورت دیگری مثل `2053` استفاده کنید (در این صورت همه‌جای این راهنما به‌جای
`8443` همان پورت را بگذارید).

#### قدم ۱ — روی سرور ایران (نقش: سرور)

پنل نصب‌شده روی سرور ایران را باز کنید ← تب بک‌هاول ← **تانل جدید**:

| فیلد | مقدار |
| --- | --- |
| نام | `main` |
| نقش | **سرور** |
| پروتکل | `tcp` |
| آدرس بایند | `0.0.0.0:3080` |
| توکن | روی دکمه‌ی ↻ بزنید و رشته‌ی ساخته‌شده را **جایی کپی نگه دارید** |
| پورت‌ها | `8443` |

ذخیره کنید. وضعیت باید سبز/فعال شود.

#### قدم ۲ — روی سرور خارج (نقش: کلاینت)

پنل نصب‌شده روی سرور خارج را باز کنید ← تب بک‌هاول ← **تانل جدید**:

| فیلد | مقدار |
| --- | --- |
| نام | `main` |
| نقش | **کلاینت** |
| پروتکل | `tcp` (باید دقیقاً با سرور ایران یکی باشد) |
| آدرس سرور | `IP_سرور_ایران:3080` |
| توکن | همان توکنی که در قدم ۱ کپی کردید، عیناً پیست کنید |

ذخیره کنید.

#### قدم ۳ — بررسی لاگ هر دو تانل

روی هر دو تانل دکمه‌ی **لاگ** را بزنید. باید این خط را (با زمان نزدیک به الان) ببینید:

```
[INFO] control channel established successfully
```

این یعنی خود تونل بین دو سرور برقرار است. اگر به‌جایش پشت‌سرهم `connection refused` یا
`i/o timeout` می‌بینید، برو به بخش «عیب‌یابی» پایین همین صفحه.

#### قدم ۴ — ساخت اینباند در Marzban/3x-ui روی سرور خارج

داخل پنل Marzban یا 3x-ui روی **سرور خارج** یک اینباند جدید بسازید با پورت **دقیقاً
`8443`** (پروتکل داخلی مثل VLESS+REALITY، VLESS+TLS، Trojan و غیره فرقی نمی‌کند، فقط
پورت باید یکی باشد). بعد از ساخت، مطمئن شوید سرویس Xray را ری‌استارت کرده‌اید.

چک کنید که واقعاً روی همان سرور (خارج) در حال گوش دادن است:

```bash
ss -tlnp | grep :8443
```

این باید یک پردازش مربوط به Xray/Marzban را نشان دهد. اگر خالی بود، اینباند ساخته یا
استارت نشده — این شایع‌ترین دلیل «وصل نمی‌شود» است.

#### قدم ۵ — ساخت لینک کانفیگ برای کاربر

از پنل Marzban/3x-ui روی **سرور خارج** لینک کانفیگ (vless/vmess/trojan) را طبق روال
عادی خودش بسازید. تنها کاری که باید دستی انجام دهید: در همان لینک، فیلد **Address**
(که پیش‌فرض IP یا دامنه‌ی سرور خارج است) را با **IP سرور ایران** جایگزین کنید. پورت،
UUID، SNI، پروتکل — هیچ‌کدام تغییر نمی‌کند.

#### قدم ۶ — تست نهایی

از یک سیستم دیگر (نه از خود دو سرور):

```bash
nc -zv IP_سرور_ایران 8443
```

اگر وصل شد یعنی مسیر باز است. حالا کانفیگ ساخته‌شده در قدم ۵ را در برنامه‌ی کلاینت
(v2rayNG، Nekoray، Streisand و مشابه) وارد کنید و تست کنید. اگر سایت `whatismyip.com`
IP سرور خارج را نشان داد، همه‌چیز درست کار می‌کند.

### سناریوی معکوس

اگر می‌خواهید برعکس شود (کاربر به **IP خارج** وصل شود ولی سرویس واقعی روی **ایران**
اجرا شود)، دقیقاً همین شش قدم را با جابه‌جا کردن نقش‌ها تکرار کنید: سرور خارج = نقش
«سرور» با `پورت‌ها = 8443`، سرور ایران = نقش «کلاینت»، اینباند Marzban هم روی ایران
ساخته می‌شود و لینک کانفیگ با IP خارج جایگزین می‌شود.

### قالب قوانین پورت

فیلد «پورت‌ها» فقط در نقش «سرور» ظاهر می‌شود و هر خط یکی از این قالب‌هاست:

| قالب | معنی |
| --- | --- |
| `443` | پورت ۴۴۳ باز شود و به همان پورت ۴۴۳ روی سمت کلاینت فوروارد شود |
| `8080=80` | پورت ورودی ۸۰۸۰، به پورت ۸۰ روی سمت کلاینت فوروارد شود |
| `2000-2100` | بازه‌ای از پورت‌ها با هم باز شوند |
| `127.0.0.1:443=443` | فقط روی یک IP مشخص از سرور بایند شود |

### عیب‌یابی بر اساس لاگ

پیام‌های واقعی که در لاگ هر تانل می‌بینید و معنی هرکدام:

| پیام در لاگ | یعنی چی | راه‌حل |
| --- | --- | --- |
| `control channel established successfully` | تونل بین دو سرور برقرار است | چیزی لازم نیست، این خط خوب است |
| `channel dialer: dial tcp ...connect: connection refused` (چند بار در ابتدا) | سمت کلاینت هنوز نتوانسته به سرور وصل شود | اگر بعدش `established successfully` آمد مشکلی نیست (تلاش مجدد خودکار). اگر ادامه‌دار بود، توکن یا پورت بایند اشتباه است یا فایروال سرور «سرور» پورت کنترل (۳۰۸۰) را بسته |
| `local dialer: dial tcp ->127.0.0.1:PORT: connect: connection refused` | تونل خودش سالم است، ولی سمت **کلاینت** روی پورت داخلی (مثلاً ۸۴۴۳) هیچ سرویسی گوش نمی‌دهد | روی همان سرور (کلاینت) اجرا کنید: `ss -tlnp \| grep :PORT`؛ اگر خالی بود یعنی اینباند Marzban ساخته/استارت نشده — قدم ۴ بالا را دوباره چک کنید |
| هیچ لاگی اصلاً ثبت نمی‌شود | سرویس systemd تانل استارت نخورده | از پنل روی همان تانل دکمه‌ی «شروع» را بزنید، یا در ترمینال: `systemctl status eris-backhaul-main` |
| کاربر نهایی هنگام اتصال «Connection failed» می‌گیرد ولی لاگ‌های بک‌هاول تمیزند | مشکل از خود کانفیگ کلاینت است، نه تونل | مطمئن شوید Address توی لینک را درست عوض کرده‌اید و UUID/SNI با اینباند Marzban مطابقت دارد |

قانون طلایی عیب‌یابی: همیشه اول لاگ **هر دو** تانل (سرور و کلاینت) را جدا جدا نگاه کنید؛
معمولاً یکی از دو طرف دقیقاً می‌گوید مشکل کجاست.

├── config.json            تنظیمات پنل (۰۶۰۰)

## نکات امنیتی / Security notes

- پنل روی **HTTP** سرو می‌شود. برای دسترسی از اینترنت آن را پشت Nginx با گواهی TLS
  قرار دهید یا فقط از طریق یک تانل SSH به آن وصل شوید.
- بلافاصله بعد از نصب، رمز عبور را از بخش **تنظیمات** تغییر دهید.
- پنل با دسترسی root اجرا می‌شود چون یونیت‌های systemd می‌سازد و مدیریت می‌کند.
- کلیدها و رمزهای SSH با مجوز `0600` ذخیره می‌شوند و هرگز در پاسخ API برنمی‌گردند.
- پورت پنل را در فایروال فقط برای آی‌پی خودتان باز بگذارید.

## اجرای محلی برای توسعه / Local development

```bash
git clone https://github.com/eris4444/eris-tunnel.git
cd eris-tunnel
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt

export ERIS_HOME="$PWD/.eris-dev"
python -m backend.cli setup --port 8686 --password admin1234
python -m backend.server
```

سپس `http://127.0.0.1:8686` را باز کنید. در این حالت مدیریت systemd کار نمی‌کند
ولی رابط کاربری و API کامل قابل بررسی است.

اجرای تست‌های خودکار / run the API smoke tests:

```bash
pip install httpx
python smoke_test.py
```
